# SQLD·ADsP 공통 테이블 / 공통 API 변경

이 문서는 로컬 구현의 계약과 배포 전 검수 절차입니다. 운영 DB 구조·데이터와 실제 동시성은 아직 검증하지 않았습니다. 마이그레이션·배포·외부 발송은 별도 승인 대상입니다.

사용자 요청에 따라 마이그레이션 SQL은 이 Git 저장소에 포함하지 않고 아래 로컬 파일로 별도 보관합니다. 애플리케이션 코드에 SQL 마이그레이션을 넣거나 시작 시 자동 실행하지 않습니다.

- 적용 SQL: `/Users/ronny/Documents/codex/2026-10-22/task/exam_scope_20261025/work/docs/exam_scope_20261025_up.sql`
- 초기 검증 단계 복구 SQL: `/Users/ronny/Documents/codex/2026-10-22/task/exam_scope_20261025/work/docs/exam_scope_20261025_down.sql`
- SELECT 전용 사전 점검: `/Users/ronny/Documents/codex/2026-10-22/task/exam_scope_20261025/work/docs/exam_scope_20261025_preflight.sql`

### 지금 SQL을 실행하려는 경우

up/down은 **실제 PostgreSQL에서 아직 검증하지 않은 1회용 마이그레이션**입니다. 이전 `Review SQLD-only legacy inventory before enabling this migration`은 의도된 보호 장치였지만 구체적인 확인 대상을 알려주지 못했습니다. 수정한 up은 일괄 `solsqld.confirm_legacy_sqld` 플래그를 사용하지 않습니다. 테이블 잠금 후 실제 컬럼·제약·인덱스와 시험/커리큘럼 코드를 검사하고, 문제와 분류의 관계를 확인한 뒤에만 DDL로 진행합니다.

시험 구분 컬럼이 하나라도 있거나 이번 마이그레이션 이름의 제약/인덱스가 있으면 DDL 전에 중단하고 **존재/누락 컬럼, 실제 타입·기본값, 제약·인덱스 정의**를 출력합니다. 8개 컬럼이 모두 있어도 성공으로 단정하지 않습니다. 재실행으로 컬럼을 덮어쓰거나 부분 상태를 자동 정리하지 않습니다. 알 수 없는 시험·커리큘럼 코드에는 건수와 실제 ID/코드 표본을, 분류 없는 문제에는 건수를 표시하며 확인 플래그로 우회할 수 없습니다.

무한풀이 분류와 과거 답안이 비어 있으면 사람 확인 없이 진행할 수 있습니다. 기존 데이터가 있으면 원래 시험 식별자가 없어 자동 증명할 수 없으므로 **분류 수·답안 수·매핑 안 된 답안 수, 분류/문제 ID 표본, 필요한 확인 문자열과 정확한 SET 명령**을 오류 DETAIL/HINT에 표시합니다. preflight 5번은 같은 확인 문자열을 조회만 합니다. 담당자가 전체 이력의 SQLD 소속을 확인한 경우에만 전용 승인 세션에서 그 명령을 사용합니다. 문자열은 분류/문제 카탈로그 지문과 이력 건수에 연결되며, 개별 답안 내용 전체를 검증하거나 건수가 같은 수정까지 감지하는 증거는 아닙니다. 검수부터 적용까지 트래픽을 중지/드레인하는 운영 계획이 필요합니다. 소속이 불명확하거나 섞여 있으면 적용을 보류합니다.

먼저 대상이 운영 `sqld_lab`인지 검증 DB인지 확인합니다. 위 preflight를 새 독립 읽기 전용 연결에서 **1번 연결 정보 → 2번 컬럼/제약 → 3번 콘텐츠 → 4번 이력 → 5번 필요한 확인 문자열 순서로 나눠** 실행하고 결과를 확인해야 합니다. 컬럼·권한이 없거나 새 컬럼이 이미 일부 존재하면 뒤 단계 및 up 실행을 멈춥니다. preflight는 확인 플래그를 자동으로 켜지 않으며 새 세션의 상태로 이전 실행 세션 상태를 판단할 수 없습니다. 기존 오류가 난 세션에 다른 미커밋 작업이 있는지 모르는 상태에서 임의로 COMMIT/ROLLBACK하지 마세요.

기존 시험·커리큘럼 코드와 무한풀이 분류·과거 답안의 SQLD 소속, 과목 과락 컬럼, 백업/복구 경로, 검증 DB 테스트 및 유지보수 계획을 확인한 뒤에만 아래 적용 절차를 진행합니다. 매핑되지 않는 답안은 삭제된 문제의 이력일 수 있어 자동 분류하지 않습니다. 매핑이 모두 된 경우도 시험 소속을 증명하는 것은 아닙니다. preflight의 집계 SELECT는 데이터가 크면 비용이 들며 자동 실행하지 않습니다.

## DB 컬럼 추가 전의 호환 배포

`app/db/exam_scope.py`가 요청 전에 읽기 전용 메타데이터로 상태를 확인합니다. 새 컬럼을 조회하다가 오류가 나면 재시도하는 구조가 아니며, PostgreSQL의 실패한 트랜잭션에서 계속 쿼리하지 않습니다.

| 스키마 상태 | SQLD | ADsP |
|---|---|---|
| 이번 마이그레이션의 새 컬럼이 하나도 없음 (`legacy`) | 기존 컬럼만 사용하는 쿼리로 동작 | 503, `X-Exam-Readiness: schema_upgrade_required` |
| 필요한 새 컬럼·과목 과락 설정·재전송 unique 인덱스 준비 (`ready`) | 시험별 쿼리로 동작 | `ENABLE_ADSP=true`일 때만 동작. 기본값은 비공개이며 503 `feature_disabled` |
| 일부만 추가됨 (`partial`) | 잘못된 범위로 조회하지 않도록 503 `schema_partial` | 동일하게 차단 |

예상된 준비 상태 응답의 `detail`은 기존 프런트엔드 오류 처리에서 표시할 수 있는 한국어 문자열이며 `Retry-After: 60`을 포함합니다. 연결 실패·예상치 못한 DB 오류는 준비 상태로 바꾸거나 숨기지 않습니다. 실제 인증 의존성은 유지합니다.

`GET /api/content/exam-capabilities`는 다음과 같은 공개 기능 상태를 반환합니다. 새 UI는 이를 이용해 ADsP 진입을 숨기거나 준비 중으로 표시할 수 있습니다.
```json
{"schemaState":"legacy","sqld":{"available":true},"adsp":{"available":false}}
```

준비 상태는 캐시하지 않습니다. 목록/대시보드 캐시를 반환하기 전에도 검사하고, 캐시 키에 스키마 모드를 포함합니다. 구 DB의 무한풀이는 기존 SQLD 클라이언트의 UUID 없는 요청을 그대로 처리합니다. 구 DB에 새 `requestId`를 보내면 중복 보호를 제공하는 척하지 않고 503 `schema_upgrade_required`로 거절합니다. 구 DB의 통계 초기화는 기존 삭제 방식, 변경된 DB에서는 이력 보존 방식입니다.

`request_id`만 존재하는 경우도 부분 마이그레이션으로 간주해 기존 삭제 경로를 차단합니다. 반대로 원래 있던 `exam.subjects.pass_threshold_percent`만 있는 것은 새 마이그레이션의 증거가 아닙니다. SQLD 구 모드 제출은 해당 설정 컬럼이나 `display_order`를 읽지 않습니다. 기존 질문의 `subject_id`와 고정 40% 기준을 사용합니다. 원본 앱 이력에는 이 설정 조회가 없었으며, 현재 저장소에 원본 과목 테이블 DDL은 없습니다. 별도 dbt Bronze 코드의 컬럼 참조는 확인했지만 운영 스키마 존재 증거로 간주하지 않습니다. ADsP 준비 판정과 up SQL의 사전 검증에서 과목 과락 설정 존재를 요구합니다.

## 저장 구조

- `exam.exams`, `education.curricula`, `endless.problem_categories`에 `exam_type` (`sqld` 또는 `adsp`)를 추가합니다. 정확히 `__UNSORTED__`인 시험 보관 행은 NULL로 보존하는 제한된 예외입니다. 문제·과목·레슨·응시·결과는 부모의 실제 ID를 통해 소속을 결정합니다.
- 기존 `id=1, exam_code='__UNSORTED__'` 행은 사용자 오류 출력으로 확인했습니다. 로컬 앱/조회한 Git 이력에서 생성 DDL이나 문자열 용례는 찾지 못했으므로 SQLD 소속이라고 단정하지 않습니다. 기존 공개 API는 `sqld_mock_` 코드만 조회했습니다. 이 정확한 코드는 미지정 컨테이너로 유지하고 ID·코드·하위 문제·과목·응시 기록을 바꾸지 않습니다. CHECK 제약으로 이 행에 sqld/adsp를 붙이는 것과 실제 시험의 NULL을 모두 금지합니다. 다른 미확인 코드와 임의의 id=1에는 예외를 적용하지 않습니다. preflight는 연결된 문제·과목·응시 건수를 따로 보여줍니다. 관리용 질문 조회에서는 연결 데이터가 쓰일 수 있으며 미사용 데이터로 간주하지 않습니다.
- 외부 문제 문자열을 저장하는 `logs.endless_answers`에는 서버가 검증한 `exam_type`을 기록합니다. `request_id`는 재전송 구분, `statistics_cleared_at`은 통계 초기화 후 중복 방지 이력 보존에 사용합니다.
- 실제 PK, 기존 unique/FK, SQLD 코드와 사용자 기록을 바꾸지 않습니다. ADsP의 `exam_code`는 `adsp_mock_1`처럼 작성합니다. 새 커리큘럼·레슨·외부 문제 코드는 기존 전역 코드와 겹치지 않아야 합니다. 자식 테이블마다 시험 종류를 중복 저장하지 않습니다.
- 사용자와 `dashboard.user_stats`의 사용자별 공통 포인트 잔액을 유지합니다. 포인트는 기존대로 모의고사 정답 1개당 1점, 무한풀이 정답당 1점입니다. 시험 배점과 보상 포인트를 혼동하지 않습니다.
- 기존 SQLD는 `grading_policy=legacy_equal`로 기존 2점/문항, 총점 60%, 과락 40%를 보존합니다. ADsP는 `grading_policy=weighted`를 명시하고 문항 JSON의 `points`, `exam.subjects.pass_threshold_percent`, `exam.exams.pass_threshold_percent`를 사용합니다. 구체적 ADsP 콘텐츠·배점 승인은 별도입니다.
- 새 제출에는 적용 채점 정책·과목 결과·결과 화면 데이터·누적 시간 기여분을 기존 JSON 스냅샷 필드에 저장합니다. 기존 `{"source":"submit"}` 스냅샷을 소급 변경하지 않습니다. 구 결과는 과거와 같은 조회 방식을 사용하므로 과거에 저장되지 않은 채점 사실을 복원했다고 주장하지 않습니다.
- 가중 채점은 배점이 없는 문항을 2점으로 보정하지 않고 거절합니다. 기본 2점 표시는 구 SQLD 변환에만 유지합니다. 백분율은 Decimal로 소수 둘째 자리까지 계산·반올림한 뒤 Decimal 기준값과 비교하고, 응답 표시값만 실수로 변환합니다.

## API 계약과 구 클라이언트

기존 URL과 응답 필드를 유지합니다. 새 호출은 `exam_type=sqld|adsp`를 반드시 명시해야 합니다. 서버는 구 SQLD 클라이언트 호환을 위해 생략 시 `sqld`로 처리합니다. 새 프런트엔드에 대한 강제 여부를 서버가 구 클라이언트와 구분할 수는 없으므로 클라이언트 계약과 테스트에서 확인해야 합니다. 잘못된 값은 422입니다.

| 기능 | 요청 예시 | 처리 |
|---|---|---|
| 모의고사 목록/상세 | `GET /api/content/exams?exam_type=adsp`, `/api/content/exams/1?exam_type=adsp` | 실제 코드 `adsp_mock_1`과 DB 소속 모두 확인 |
| 개념학습 목록/목차 | `GET /api/education/curricula?exam_type=adsp`, `/api/education/curricula/adsp_concept?exam_type=adsp` | 커리큘럼 소속 확인 |
| 레슨 | `GET /api/education/lessons/301?exam_type=adsp` | 부모 커리큘럼을 통해 소속 확인 |
| 진도 | `GET/PUT /api/education/lessons/301/progress?exam_type=adsp` | 본인·레슨·공개 버전·시험 소속 확인 |
| 시작/재개 | `GET /api/exams/1/session?exam_type=adsp` | 기존 시작/재개 동작, 응시 UUID 반환 |
| 답안/메모/시간 | 기존 `/api/exams/1/answers`, `/memo`, `/session`의 PUT | 시험 종류 + `attemptUuid`로 실제 응시 검증 |
| 제출 | `POST /api/exams/1/submit?exam_type=adsp` | 응시 소속·사용자·상태 확인, 재전송 추가 적립 없음 |
| 결과 | `GET /api/exams/1/result?exam_type=adsp&attempt_id=700` | 기존 실제 `attempt_id` 필터와 사용자 검증 유지 |
| 무한풀이 | 기존 `/api/endless/problems`, `/answer`, `/stats` | 조회·답안·통계·초기화를 같은 시험으로 제한 |
| 대시보드 | `GET /api/dashboard/summary?exam_type=adsp` | 시험별 학습 기록, 공통 포인트, SQL 실습 목록은 비움 |

진도 본문 예시:
```json
{"lessonVersionId":901,"completed":true}
```
응시 저장/제출 본문 예시(실제 세션에서 반환한 UUID 사용):
```json
{"attemptUuid":"00000000-0000-0000-0000-000000000700","remaining_seconds":120,"current_page_no":1}
```
무한풀이 본문 예시(같은 논리 제출의 재시도에는 같은 UUID 재사용):
```json
{"requestId":"00000000-0000-0000-0000-000000000701","problem_id":"adsp_q1","selected_answer":"1"}
```

ADsP 저장에는 `attemptUuid`, 무한풀이에는 `requestId`가 필수입니다. SQLD 구 클라이언트의 해당 필드 생략은 허용합니다. 따라서 UUID 없는 구 무한풀이 호출은 재시도와 새 풀이를 구분할 수 없습니다. 새 SQLD 프런트엔드도 UUID를 보내야 합니다. 요청 ID를 다른 시험/문제/답안에 재사용하면 409입니다. 상세·진도·응시의 소속 불일치는 404이며, 제출 후 답안 변경은 409입니다.

일정 API만 기존 예외를 유지합니다: `/api/exams/schedules`에서 시험 구분 생략은 전체 일정, 기존 표시명 필터는 그대로 허용합니다. `sqld` 입력은 로컬 SQL에 확인된 `SQL 개발자` 값도 조회합니다. 새 ADsP 일정은 `adsp`로 등록합니다. 운영의 다른 일정 표기값은 아직 확인하지 않았습니다.

공통 로그인/회원 API는 변경하지 않습니다. SQL 실습은 기존 SQLD 기능으로 유지합니다. `/sqld/...`, `/adsp/...` 화면, 선택 상태, 프런트엔드 캐시/스토리지 키 및 API 래퍼의 명시적 scope/UUID 연결은 별도 A안 UI 작업입니다. 현재 UI가 ADsP를 지원한다고 주장하지 않습니다.

## 통계와 중복 처리

- 목록 캐시는 시험 종류별, 대시보드는 `(user_id, exam_type)`별입니다. 캐시를 사용해도 공통 포인트는 매번 현재 잔액을 읽습니다. 학습 통계의 기존 TTL은 유지합니다.
- 대시보드 캐시는 잠금 안에서 독립 복사본을 만든 후 잠금을 풀고 연결 풀·DB를 조회합니다. 캐시 저장 시에도 별도 복사본을 사용하므로 응답의 중첩 객체 변경이 캐시를 변경하지 않습니다. 한 사용자의 느린 잔액 조회가 다른 사용자의 캐시 조회를 막지 않는 회귀 테스트를 포함합니다.
- 기존 SQLD의 누적 카운터는 과거 무한풀이 기록 삭제 후에도 유지되어 왔습니다. 단순 원천 재집계로 기존 수치를 바꾸지 않도록, 새 ADsP 기여분을 원천에서 계산하고 SQLD는 기존 공통 누적값에서 ADsP 기여분만 뺍니다. ADsP 학습 시간은 새 제출 스냅샷의 정확한 기여분을 사용합니다. 한 SQL 문에서 동일 시점의 누적값과 기여분을 읽습니다. 이 방식은 **기존 데이터가 SQLD뿐이고 ADsP는 이 버전으로 새로 시작한다는 전제**를 갖습니다. 기존 ADsP 데이터가 있으면 마이그레이션을 중단하고 별도 정합성 작업이 필요합니다.
- ADsP 답안은 통계 초기화 시 삭제하지 않고 표시만 초기화합니다. 누적 카운터와 재전송 식별자는 보존됩니다. 이 변경은 개인정보 탈퇴/삭제 API를 대신하지 않습니다.
- 모의고사/무한풀이 작성은 기존 사용자 통계 행을 잠가 같은 사용자의 응시 생성·적립을 직렬화합니다. 실제 응시 UUID 조회도 행 잠금을 사용합니다. 상태 전환·결과·잔액은 같은 DB 트랜잭션입니다. 실제 PostgreSQL 경합 검증은 별도입니다.
- 기존 SQLD 분석/dbt/Slack 리포트는 이 변경에 포함하지 않았습니다. ADsP 데이터가 들어오기 전에 기존 분석 쿼리가 시험 범위를 구분하도록 확인해야 합니다. 공통 로그인/사이트 DAU를 임의로 두 시험에 복제하지 말고, 전체 고유 사용자도 시험별 고유 사용자의 합으로 계산하지 않아야 합니다.

## 적용 및 되돌리기

1. **DB 변경 없이 호환 백엔드를 먼저 배포할 수 있습니다.** `ENABLE_ADSP`는 설정하지 않거나 false로 둡니다. 구 DB의 SQLD 동작과 ADsP 준비 중 응답을 승인된 검증 환경에서 확인한 뒤, 확인된 배포 대상으로만 릴리스합니다.
2. 이후 DB 변경을 별도 승인받고 검증 DB에서 현재 테이블/제약과 데이터 수를 확인합니다. 운영 DB에 자동 연결하는 스크립트는 없습니다. 원본 백업·포인트 총합·사용자 수·SQLD 콘텐츠/응시/진도 수를 기록합니다.
3. 기존 시험 코드가 `sqld_mock_`이고 커리큘럼 코드가 `sqld`로 시작하는지 확인합니다. 기존 무한풀이 분류·답안은 시험 구분 근거가 없으므로 모두 SQLD인지 사람이 확인해야 합니다. 알 수 없는 콘텐츠를 SQLD로 자동 분류하지 않습니다.
4. 알려진 SQLD 코드와 빈 무한풀이 데이터라면 별도 확인 플래그 없이 up의 검증을 통과합니다. 기존 무한풀이 데이터가 있으면 전체 소속을 확인한 뒤, up의 DETAIL/HINT에 나온 **현재 목록과 연결된** `solsqld.confirm_legacy_endless` 설정을 전용 승인 세션에 적용하고 전체 up을 한 번 실행합니다. 이 확인은 실행 승인을 대신하지 않습니다. 알 수 없는 시험/커리큘럼은 DDL 전에 중단되고, 재실행/부분 적용 상태에는 정확한 메타데이터를 반환합니다. 오류 이후 클라이언트가 다음 문장을 자동 실행하지 않게 설정하며 임의 COMMIT/ROLLBACK은 하지 않습니다.
5. 모든 API 인스턴스를 호환 버전으로 전환하고 마이그레이션 전 요청을 종료/드레인한 뒤 SQLD 회귀 검증을 완료합니다. 구 서버는 새 query를 무시하거나 무한풀이를 전체 조회하므로 **구/신 버전 혼재 또는 마이그레이션 전 요청이 진행 중일 때 ADsP 콘텐츠를 넣거나 공개하지 않습니다.**
6. 승인된 ADsP 콘텐츠·과목 배점으로 같은 사용자 시나리오, 잘못된 시험 ID, 동시 제출, 재전송, 통계 초기화 후 재시도, 장애 롤백을 검증합니다. 기존 SQLD 점수/잔액/카운터 대조도 필요합니다.
7. 프런트엔드 scope·UUID 연결 및 분석 파이프라인 구분 확인 후 별도 승인으로 `ENABLE_ADSP=true`를 설정해 공개합니다.

초기 검증 단계에는 위 별도 경로의 `exam_scope_20261025_down.sql`로 컬럼/인덱스만 되돌릴 수 있습니다. ADsP 또는 request/reset 상태가 생기면 down은 의도적으로 실패합니다. 사용 이후에는 추가 컬럼과 기록을 유지하고 호환 수정본으로 복구합니다. 구 서버로 단순 복귀하면 ADsP 데이터가 섞일 수 있습니다. 포인트 과거 백업 복원, 사용자/응시/진도 삭제는 롤백 방법이 아닙니다.

down SQL은 독립 트랜잭션에서 READ COMMITTED를 명시하고, 보호 대상 4개 테이블의 ACCESS EXCLUSIVE 잠금을 **안전 조건 검사보다 먼저** 획득합니다. 이미 진행 중인 쓰기가 완료된 뒤 최신 상태를 검사하며 이후 쓰기는 COMMIT까지 차단합니다. 잠금 획득 제한은 5초이고, 실패 시 삭제를 진행하지 않습니다. 파괴적 롤백 전에는 API 요청도 드레인해야 합니다. 잠금·검사 순서의 정적 회귀 검사는 별도 작업 폴더의 `test_migration_guard_order.py`에 있으며, 실제 PostgreSQL 경합 검증을 대신하지 않습니다.

## 로컬 파일로 확인한 배포 경로와 미확인 사항

- 앱 저장소 원격: `github.com/BeolLe/sqld_project`, 브랜치 `main`. `.github/workflows/backend-ghcr.yaml`은 `main`의 `backend/**` 변경 push 시 `ghcr.io/beolle/sqld-backend:latest` 및 SHA 태그 이미지를 빌드·게시합니다. 따라서 이 경로에는 commit/push 및 이미지 발행이 수반됩니다.
- 로컬 GitOps `infra/argocd/argocd-back.yaml`은 `BeolLe/sqld_project_gitops/main`, `infra/backend`, ArgoCD `back-k8s`, 네임스페이스 `app`을 지정합니다. Image Updater는 SHA 태그를 GitOps main에 기록하도록 설정돼 있습니다.
- 공개 서비스 `infra/apps/sqld/overlays/public`은 `app-public`을 지정합니다. 로컬 README는 해당 경로를 관리하는 Application이 관리 목록에 없다고 명시합니다. **자동 갱신 `app`과 공개 서비스 `app-public`을 같은 배포로 취급하지 않습니다. 실제 사용자 서비스의 배포 대상은 확인이 필요합니다.**
- 로컬 `.argocd-source-back-k8s.yaml`은 `sha-fab54d0`, 기본 deployment 파일은 `sha-00dc9aa`를 가리킵니다. 이는 현재 실행 이미지나 정상 롤백 버전을 확인한 증거가 아닙니다. 운영 상태/이미지 다이제스트/ArgoCD 동기화 결과는 아직 조회하지 않았습니다.
- 이 작업에서 클러스터 접속, 이미지 게시, commit/push, DB 실행은 수행하지 않았습니다. 배포 대상을 확인하고 필요한 게시 권한·검증 환경 접근 범위를 정한 뒤 진행해야 합니다.

## 검증

설치된 uv 가상환경을 사용하며 의존성 설치나 서비스 시작은 하지 않습니다.
```sh
cd backend
.venv/bin/python -I -B tests/run_exam_scope_isolated.py
```
하네스는 실제 설정·인증정보·DB 풀·외부 발송 클라이언트를 로드하지 않고 네트워크/서브프로세스/파일 쓰기를 차단합니다. 테스트는 순수 채점, HTTP 파라미터 검증, 소유권 SQL 조건, 캐시 분리, 트랜잭션 분기와 재전송을 가짜 연결로 검증합니다. 실제 인증 서버, PostgreSQL SQL 실행/잠금/마이그레이션, 프런트엔드 E2E, 운영 발송을 검증한 것은 아닙니다.
